# Migrating from package `0.11.0` to `1.0.0`

This guide describes what changes for a consumer when the package moves from
private `0.11.0` to `1.0.0`. Package `0.11.0` is private and unpublished, and
this guide does not authorize a publication.

## What changes

The change is to support guarantees, not to behavior. Package `1.0.0` adopts
`packagePolicyVersion` `1.0.0` of the [compatibility
policy](../../spec/compatibility.md), which classifies every declared package
surface and places all of them under Semantic Versioning protection.

- Every root runtime export, root type export, and root `DomainErrorCode` value
  becomes Stable Public API. Removing one or changing its meaning requires
  package `2.0.0`.
- The generic `collective-cognition` executable becomes Stable Public API. Its
  command names, machine-readable success output, diagnostics, and exit
  behavior are protected.
- The Markdown adapter, connector conformance, the Team Memory and Git
  connectors, host conformance, the reference host, the SQLite stores, the
  durable workflow, and the three dedicated executables keep the Supported
  Experimental label. Under policy `1.0.0` that label describes operational
  maturity only. Those surfaces are SemVer protected and remain
  import-compatible through package `1.x`.
- The `minor-before-1.0` package-version effect is withdrawn. A breaking
  public-package change now requires a major release.

## What does not change

Portable Cognition `0.1.0` record meaning does not change. A record that a
`0.11.0` consumer wrote is read identically by a `1.0.0` consumer, and a record
that `0.11.0` rejected is still rejected. The same holds for SourceRecord
`0.1.0`, Host Integration `0.1.0`, and every other immutable versioned
contract, schema, fixture, and profile the package distributes.

Package `1.0.0` is not a Portable Cognition `1.0.0`. No `1.0.0` implementation
reinterprets an existing `0.1.0` record as if it were authored against a newer
schema, and existing records stay readable through explicit contract-version
dispatch.

## What a consumer has to do

Nothing, to keep working. There is no source change, no import change, no
serialized-data migration, and no configuration change between `0.11.0` and
`1.0.0`.

Two habits change instead:

1. Read the classification in `STAB-002` of the compatibility policy before
   relying on a surface. It states exactly which package surfaces carry a
   guarantee.
2. Expect an incompatible change to a root export, to the generic executable,
   or to an existing versioned subpath to arrive as package `2.0.0` or as a new
   versioned subpath beside the retained old one, never as a `1.x` release.

## What is still not promised

Policy `1.0.0` does not claim production readiness, certification, endorsement,
or long-term support, and it does not confirm registry-name availability or
remove the package publication guard. A release governed by this policy version
requires its own compatibility baseline, distribution-readiness profile, and
accountable-human publication approval.
